## Overview

v1.7.3 是一次大规模架构重构版本。相比 v1.7.2，框架完成了包结构重组、引擎拆分、异常体系分散化、资源生命周期管理、初始化系统子包化五项核心改造，同时修复了分布式模式下多个关键缺陷。

**兼容性策略分两层：**

- **包结构重组部分**（`extension/` → `extensions/`、`factories/` → `core/`、`scheduling/` → `commands/` 等）：旧 import 路径已全部删除，**不保证向后兼容**，升级时需要按下方迁移指南调整。
- **初始化系统子包化部分**（`application.py` → `core/initialization/` 子包）：通过 PEP 562 `__getattr__` 延迟 re-export 23 个符号，**100% 向后兼容**，22 处生产代码 `from crawlo.core.application import initialize_framework` 全部零修改工作。

### 3. 初始化系统子包化（application.py 瘦身）

v1.7.2 的 `core/application.py` 仅 171 行。v1.7.3 初版将其扩展至 1670 行，整合了原 `initialization/` 包的全部职责（6 个文件的初始化逻辑合并为单一入口）。但单文件承载三层职责（全局状态容器 + DI 容器 + 阶段化初始化系统）已逼近可维护边界，因此本次再次重构：**将初始化系统从 application.py 物理抽离为独立子包 `crawlo/core/initialization/`**。

**重构前后对比：**

| 指标 | 重构前 | 重构后 |
|---|---|---|
| `application.py` 行数 | 1707 行 | 771 行（当前，-55%） |
| 初始化系统组织 | 单文件内三大职责混合 | 7 个内聚文件，每个 42-332 行 |
| 外部引用破坏 | — | 0（22 处 `from crawlo.core.application import initialize_framework` 全部零修改） |

**新子包结构：**

```
crawlo/core/initialization/
├── __init__.py     # 106 行  公共 API 导出（28 个符号）
├── phases.py       # 203 行  阶段定义 + 依赖校验（DFS 三色标记法检测循环依赖）
├── context.py      # 116 行  InitializationContext（线程安全 RLock 保护）
├── utils.py        #  42 行  工具函数（create_initialization_result / InitializationTimer）
├── registry.py     # 166 行  Initializer + InitializerRegistry + 全局解析（DI 容器优先 + fallback）
├── built_in.py     # 332 行  5 个内置初始化器（Logging/Settings/CoreComponents/Extensions/FrameworkStartupLogger）
└── core.py         # 192 行  CoreInitializer（单例 + 阶段化编排 + 超时隔离 + fallback 兜底）
```

**依赖方向（无循环）：**

```
phases → context/utils → registry → built_in → core
                  ↑
            application.py（不依赖 initialization，通过 __getattr__ 延迟 re-export）
```

**关键设计决策：**

| 决策 | 实现方式 | 价值 |
|---|---|---|
| **依赖方向无循环** | `initialization/*` → `application`（单向）；`application` 不依赖 `initialization` | 避免 import 期循环 |
| **100% 向后兼容** | `application.py` 用 `__getattr__` 延迟 re-export 23 个初始化符号（PEP 562） | 22 处外部引用零修改 |
| **延迟加载** | re-export 通过 `__getattr__` 触发，模块加载期不拉 initialization 子包 | 避免 import 期重量级副作用 |
| **身份一致性** | re-export 缓存到 `globals()` 后返回同一对象引用 | `is` 检查成立，7 处 `initialize_framework` 同一 id |
| **单文件拆分原则** | Mixin 适合横向能力复用（请求生成）；组合适合状态机隔离（分布式协调） | Engine 拆分的教科书做法 |

**application.py 瘦身后的职责：**

- `ApplicationContext` — 全局状态容器，组合三个内聚子上下文（`RegistryContext` / `NotificationContext` / `RuntimeContext`）
- `Container` + `@inject` — DI 容器，支持 SINGLETON/TRANSIENT/REQUEST 三种作用域
- 23 个初始化符号通过 `__getattr__` 延迟 re-export，保持 `from crawlo.core.application import initialize_framework` 向后兼容

## New Features

### ResourceScope — 资源作用域管理

新增 `crawlo/core/resource_scope.py`，解决两个生产场景：

**场景 1：多爬虫共享资源**

同一项目内多个爬虫并发运行时共享数据库连接池，所有爬虫结束后统一释放。通过 `shared_resource_scope(tag)` 上下文管理器 + 连接池引用计数实现：

```python
async with shared_resource_scope('batch') as scope:
    tasks = [cp.crawl(spider_name) for _ in range(N)]
    await asyncio.gather(*tasks)
# 所有 crawler.close 完成后，ref_count 归零，共享池自动释放
```

**场景 2：定时任务长期运行**

调度器连续运行数月/数年时，内存和数据库连接数不随时间线性增长。通过以下机制保障：

- **`WeakBound`** — 弱引用包装 `Crawler` 和 `settings`，旧轮次 Crawler 被 GC 后自动返回 None，不阻断回收
- **`ObjectCounter`** — 按 GC 类型累计计数 + 最小二乘斜率计算，检测对象是否线性增长
- **`PoolSnapshot`** — MySQL/Redis/Mongo 连接池实例数与总连接数快照对比
- **`on_iteration_end(tag)`** — 每轮调度结束后推进事件循环、执行 GC 全代回收、对比基线快照检测泄漏

### Pipeline Stub 属性兜底

`crawlo/pipelines/base_pipeline.py` 新增 `_StubStats`、`_StubSettings`、`_StubCrawler`。`crawler` / `settings` / `stats` 三个 property 在资源释放后自动切换到 Stub 对象，保证 close 收尾阶段不抛 `AttributeError`。

### PipelineManager 幂等 close

`crawlo/pipelines/manager.py` 新增 `_closed` 标志，防止 SPIDER_CLOSED 事件回调重入导致的资源提前释放。

### 扩展层弱引用改造

- `crawlo/extensions/monitor/base.py` — `BaseMonitorExtension` 的 `crawler` / `settings` 改为 `WeakBound` property
- `crawlo/extensions/health_check.py` — 子 task 追踪 + cancel + `_safe_log`，确保 logger=None 时不抛错

### EventloopLagProbe

新增 `crawlo/extensions/eventloop_lag.py`，采样事件循环延迟，输出 p50/p95/p99 分位数到 stats。

### 主动 XCLAIM 扫描

分布式模式下，Engine 主动扫描 Redis Stream 的 Pending Entries List，回收超时未确认的消息，避免 Worker 异常退出后消息长期积压。

### RingBuffer 指标

新增 `crawlo/utils/ring_buffer.py`，为 Downloader 和 Pipeline 提供轻量级 p99 延迟采样。`aiohttp_downloader.p99_response_ms` 和 `generic_sql.p99_latency_ms` 直接暴露属性，`LogIntervalExtension` 每 tick 读取写入 stats gauge。

## Upgrade Guide

从 v1.7.2 升级到 v1.7.3，需按以下步骤调整：

### 1. 全局替换 import 路径

```bash
# extension → extensions
find . -name "*.py" -exec sed -i '' 's/crawlo\.extension\./crawlo.extensions./g' {} +

# factories → core
find . -name "*.py" -exec sed -i '' 's/crawlo\.factories\.registry/crawlo.core.component_registry/g' {} +
find . -name "*.py" -exec sed -i '' 's/crawlo\.factories\.base/crawlo.core.component_base/g' {} +
find . -name "*.py" -exec sed -i '' 's/crawlo\.factories\.crawler/crawlo.core.factories/g' {} +

# initialization → core.initialization（可选，application.py 已通过 __getattr__ 向后兼容）
# 若希望使用新路径，可执行以下替换；不替换也完全可用
find . -name "*.py" -exec sed -i '' 's/crawlo\.initialization/crawlo.core.initialization/g' {} +
# 保留 `from crawlo.core.application import initialize_framework` 等用法无需任何修改

# scheduling → commands
find . -name "*.py" -exec sed -i '' 's/crawlo\.scheduling\.scheduler/crawlo.commands.scheduler/g' {} +
find . -name "*.py" -exec sed -i '' 's/crawlo\.scheduling\.job/crawlo.commands.job/g' {} +
find . -name "*.py" -exec sed -i '' 's/crawlo\.scheduling\.registry/crawlo.commands.registry/g' {} +
find . -name "*.py" -exec sed -i '' 's/crawlo\.scheduling\.trigger/crawlo.commands.trigger/g' {} +

# network → http
find . -name "*.py" -exec sed -i '' 's/crawlo\.network/crawlo.http/g' {} +

# config → core.config
find . -name "*.py" -exec sed -i '' 's/crawlo\.config/crawlo.core.config/g' {} +
```

### 2. 检查异常 import

```python
# v1.7.2（集中式 crawlo.exceptions）
from crawlo.exceptions import CrawloException, SpiderError, QueueError, HttpError

# v1.7.3（异常体系拆分：基础异常收敛到 core.errors；
# 其余领域异常使用更具体的命名，并内聚在各自子包的 exceptions.py 中）
from crawlo.core.errors import CrawloException           # 全框架根异常（原 CrawloException）
from crawlo.core.errors import ScheduleException         # 调度/队列根异常
from crawlo.spider.exceptions import SpiderException     # Spider 领域根异常
from crawlo.http.exceptions import RequestException      # HTTP/Download 领域根异常
from crawlo.http.exceptions import DownloadError, RetryError, IgnoreRequestError
from crawlo.queue.exceptions import QueueFullError, QueueEmptyError, QueueClosedError
```

> 说明：`SpiderError / QueueError / HttpError` 这三个旧统称类在 v1.7.3 中已经不存在，
> 请按实际捕获粒度替换成上面列出的具体异常，或直接捕获各领域的根异常
>（`SpiderException / ScheduleException / RequestException`）。

### 3. 检查接口 import

```python
# v1.7.2（集中式 interfaces 包）
from crawlo.interfaces import ISpider, IDownloader, IPipeline

# v1.7.3（接口定义随领域分散；框架内部通常以 Protocol 形式内聚于各子包，
# 业务侧一般通过继承对应基类或鸭子类型即可，无需直接 import ISpider/IDownloader 等接口）
# - 若使用前接口仅用于类型注解，推荐直接替换为对应基类：
from crawlo.spider import Spider
from crawlo.downloader import DownloaderBase
from crawlo.pipelines import BasePipeline
```

### 4. 检查 settings.py 中的扩展路径

```python

    'crawlo.extension.log_interval.LogIntervalExtension': 100,

    'crawlo.extensions.log_interval.LogIntervalExtension': 100,
```

涉及 `crawlo.bot` 及其子包（channels / core / monitoring / templates / utils）
